# 项目文档评审

按用户指定的文档、问题和范围评审，给出有证据、可执行的最小修复建议。区分只评审与已授权的文档修订；文档评审本身不启动代码实现或部署。

## 建立评审依据

- 从当前仓库的 `AGENTS.md` 和文档索引进入，只读本次任务需要的设计、协议、调用方及实现。Acorn 的文档入口为 `docs/README.md`。
- 区分现行合同、待实施方案、审核讨论与执行记录。比较同一版本和阶段的陈述；待实施方案与当前实现不同，本身不构成矛盾。
- 以用户的显式决定为准。历史讨论仅用于核实决定及取代关系；已接受的限制和延期事项，只有发现新的冲突或具体影响时才重新提出。
- 关键结论依赖第三方接口、默认配置或版本行为时，核对对应版本的官方文档或源码，并给出来源。缺少材料或未实际运行时，明确结论的证据边界。

## 核查维度

| 维度               | 判断依据                                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 自相矛盾           | 同一条件下是否要求不同结果；跨文档的职责、状态转换、数据形状、错误分类与生命周期是否一致。指出冲突的两处陈述。                               |
| 明显缺陷或合同缺口 | 从文档支持的输入、资源和状态出发，推演关键路径，检查接纳、执行、确认、持久化与释放能否衔接。说明具体触发条件和可观察后果。                   |
| 过度设计           | 新增组件、数据结构、检查、恢复或验证流程是否解决约定需求或已观察问题，是否可以复用现有能力。按本期目标判断成本，不擅自套用生产级可靠性标准。 |
| 冗余与重复         | 同一合同是否多处独立维护；是否混入已失效方案、问答或逐版本检查流水。选择完整定义所在位置，其余引用；任务与验收为可核查性保留的摘要可以存在。 |
| 防御性表述         | 删除后若不损失合同、适用边界、设计理由或实施信息，建议删除或合并。不按“不、仅、无需”等词机械删句，也不推断作者动机。                         |

保留实质性的保证边界，例如接纳不等于完成、调用超时不证明业务失败、观测结果覆盖的范围，以及缓冲配置的实际约束。不要因删减措辞而扩大系统承诺。

只推演与变更相关的关键路径。补充机制应对应具体需求或缺陷，不为可能遭到的质疑引入额外框架、状态机、恢复扫描或完整故障矩阵。

## 评审交付

先说明整体是否自洽及主要问题，按影响排列实质发现；编辑性问题可合并成表格。每项发现包含：

- **位置和证据**：可点击的文件位置、必要的短引文或相互冲突的引用；外部行为附官方来源。
- **条件和影响**：什么情况下出现什么结果，为什么影响约定合同或实施；明确区分确定缺陷、条件性风险、合同待澄清及可选精简。
- **最小修复**：建议修改哪条合同或哪处表述，优先使用已有职责与结构；需要用户决定的行为列出可比较的选项。

冗余和防御性表述给出具体句子及删除、合并或替换建议。没有证据支持某类问题时直接说明，不为覆盖所有维度凑发现，也不将已接受的范围限制重新包装成缺陷。

只评审时直接返回结论；是否另存审核记录遵循用户要求和仓库规则。收尾说明实际阅读和检查范围、未验证部分，以及仍需处理的问题。

## 根据决定修订

- 落实本轮和会话中仍有效的已确认决定；授权充分时直接完成修订。仅在新增且未解决的决定影响外部行为、职责或范围时提问，同时继续独立工作。
- 用户明确要求不写入文档的议题，不添加到设计、审核记录、待办或执行说明；已有相关评审陈述按该要求清理。
- 根据材料是现行合同还是待实施方案确定同步范围。同步受影响的调用方合同、任务定义、完成条件、验收条目、审核决定和执行清单；保留稳定编号及已有完成状态。
- 设计保存最终合同、理由和验收要求；审核记录保存讨论与决定；执行记录保存实际进度、检查结果和剩余工作。遵循仓库的目录和命名规则，避免在索引或功能 README 中积累评审流水。
- 合并重复说明时，确认输入限制、失败行为、资源归属和已接受的保证边界仍可找到。未实施的行为不写成已实现，未通过的检查不改记为通过。

## 验证与收尾

使用项目现有文档格式工具，检查修改范围内的本地链接、锚点及受影响的入链。编号、任务或依赖变化时，核对稳定性、唯一性、清单对应关系与依赖循环。

纯文档修订使用文档检查，无需程序构建、数据库或沙箱验收。最终列明改动文件、落实的决定、实际检查及剩余限制；不将文档检查结果表述为运行行为已经验证。
