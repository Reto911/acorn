## 2. D02 与 D04 的解释

D02 原表述混合了运行架构和部署流程。“单后端实例”指只运行一份包含 API、Scheduler 和审查队列的后端进程，并非在线升级；一个后端仍可连接多个 Worker。现已按用户决定删除旧库切换流程，部署从空 MySQL 数据库开始。

D04 原来将三项独立差异合并，容易让用户不清楚需要决定什么。R01 拆为以下三项建议，R02 用户已确认接受：

| 差异项 | 已确认方案 | 影响 |
| --- | --- | --- |
| 用户名长度 | VARCHAR(255) 加完整唯一键 | 原 SQLite 没有此长度限制；当前预置测试用户不受影响，但未来用户名最多 255 字符 |
| ID 正值职责 | 保持有符号自增主键，显式 ID 正值由预置和后端边界保证 | MySQL 自增列不允许同样的 CHECK；数据库不再用原 CHECK 拦截所有人工非正 ID 写入 |
| 普通只读网络失败 | 当前请求失败，服务继续；关键写入失败仍退出 | 原 SQLite 实现将 SQLx I/O 归为严重错误，MySQL 网络断连需要与服务端存储损坏区分 |

D04 的确认范围是上述长度、职责和服务失败行为。详情见[字段差异](../09-mysql-migration-design.md#43-d04-已确认的差异)和[故障处理](../09-mysql-migration-design.md#6-错误与健康观测)。

## 3. 其他问题的答复与修订

### 3.1 配置、密码和连接占用

针对 R01 其他问题 2–6，方案将 endpoint、数据库名和用户名放在 TOML 中，密码由进程环境变量 MYSQL_PASSWORD 提供。这样密码不需要放入端点 URL；正式程序不自动加载 .env，开发临时入口可按授权读取该文件后构造配置和子进程环境。该方式由 R01 提出，R02 用户已确认。

acquire_timeout_ms 限制取得可用连接的整个过程，既包括连接已被占满时的等待，也包括新连接握手、鉴权／初始化和复用检查。池内空闲连接可保持网络连接而不被业务占用；查询读取和事务期间会借用连接，归还后才供另一操作使用。Worker 执行和 LLM HTTP 等待不持有连接。五个连接设置的逐项含义已写入[第 3.1 节](../09-mysql-migration-design.md#31-配置密码与连接池)。

### 3.2 类型容量、RESTRICT 和结构版本

针对其他问题 7–9：结构版本 4 用于全新初始化；LONGBLOB 约 4 GiB 的单列容量覆盖当前 64 KiB 单项和 8 MiB 合计预算，实际应用及传输预算保持原值。RESTRICT 保护仍被引用的身份：已有提交引用的题目版本不能被删除或更改其键；它不阻止正常状态更新。原 SQLite SQL 已有相同的外键行为。

### 3.3 运行期事务、1062 和手动审查

针对其他问题 10–13：原“数据库创建”表述已改为“创建提交记录”。第 5 节是运行中收到提交／审查 HTTP 请求后的操作，部署建库在第 7 节。

1062 是主键或唯一键重复。两个同键提交可能同时读取到“不存在”，由唯一键使其中一个 INSERT 成功，另一个读取已有提交并比较内容；这不是重新插入或重复判题。

第 5.2 节处理 finished 提交的手动审查。例如两个页面同时启动同一提交的审查，先取得行锁的事务保存 PENDING，后一个随后读取最新 PENDING 并复用；只发起一次活动审查，多余队列许可释放。expected_review_id 保护页面所见的旧结果，防止无意覆盖下一轮。

用户同意在不冲突原业务合同的前提下沿用第 5 节。实现差异已列入[第 5.4 节对照](../09-mysql-migration-design.md#54-与原-sqlite-实现的对照)：单连接／短写事务改为多连接、唯一键竞争和局部行锁；业务判断顺序、固定版本、终态、最新审查和保存后 ACK 保持。审查完成继续保留原短事务，没有新增状态或恢复流程。

另外，MySQL 中题目发布可与创建并行提交；提交仍在读取发布指针时固定版本，不追随此后发布的新版本。原 SQLite 短写事务会让其他发布写入等待，这项并发时序差异已单列。

### 3.4 COMMIT 结果不明

针对其他问题 14：MySQL 可能已经完成 COMMIT，但成功响应返回前网络断开。后端收到错误，无法据此判断数据库是否已经提交。因此记录实际故障，不把“没有收到成功响应”写成“肯定未提交”，关键写入仍按既有退出和重启规则处理，不自动重做写入。

### 3.5 任务与文档组织

针对其他问题 1、15–19：预置 SQL 直接按现有内容转换；不再安排旧数据处理。设计正文删除原第 8、9 节，第 10 节改为 checkbox 待办步骤，任务 M05、M08 及验收 V06 撤销；其他编号不重排。

审核记录迁入本目录，实施记录放在对应目录。设计第 12 节仅保留入口。长期记录位置规则已写入 AGENTS.md，当前任务的状态与检查仍保存在项目记录中。

### 5.2 READ COMMITTED 与默认隔离等级

READ COMMITTED 是事务隔离等级，InnoDB 默认使用 REPEATABLE READ。普通一致性读取中，前者每条语句建立新的已提交数据快照；后者在同一事务内复用首次读取的快照。锁定读取如 SELECT FOR UPDATE 使用自己的锁定规则，不能把普通读取的快照规则直接套用。

选择 READ COMMITTED 的项目依据是固定不可变题目版本、唯一键裁定幂等、短事务行锁接纳以及带状态／审查 ID 条件的更新；这些合同不依赖重复读取范围得到相同集合。该等级也减少范围锁定读取／更新的间隙锁，但外键和唯一键检查仍可能加间隙锁，不能据此承诺没有死锁。规则依据 [MySQL 隔离等级说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

REPEATABLE READ 也能实现当前合同；1062 分支结束原事务后在新事务读取，同样可以看见竞争方已提交的记录。READ COMMITTED 是与本方案并发实现匹配的选择，不是迁移必需条件，不宣称已经验证性能优势。R02 仅解释理由，当时未将用户询问记为同意更改隔离等级；后续 R03 已获用户明确确认。

### 5.3 手动审查与事务边界

“手动”指用户点击触发，执行者仍是 LLM。短事务只负责接纳：锁定提交行，检查状态并保存新 review_id 和 PENDING，随后提交、释放行锁并归还连接，再交接审查队列。

排队后读取固定输入到内存，归还连接，再发起并等待 LLM 请求；这段网络等待不持有数据库事务、行锁或借出的连接。结果返回后重新获取连接，用另一短事务读取源码校验，并按 id、review_id 和 PENDING 条件保存、提交。PENDING 是持久化业务状态，不代表保持事务打开。

这沿用[既有审查队列与执行合同](../08-llm-code-review-design.md#72-队列与执行)，不是本次迁移新增的长事务。阶段及资源边界已明确写入设计第 5.2 节。
