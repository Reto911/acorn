## 3. 排队、在线观测与交接窗口讨论

### 3.1 任务等待

已确认后端按事件及明确错误推进任务，待接纳任务按容量排队，Worker 保留执行期限、资源限额及停止合同。正文只维护这个做法，删除此前替代方案的讨论。消息交接及健康采集继续按各自调用预算执行。

### 3.2 通过消费组观测 Worker 在线

可以查询任务组成员，借用 broker 心跳检测的结果，无需新心跳消息或 Worker 注册表。rdkafka 0.39.0 已提供 [fetch_group_list](https://docs.rs/rdkafka/0.39.0/rdkafka/client/struct.Client.html#method.fetch_group_list)；实际使用按组协议和权限验证。

已确认后台采集和缓存：新鲜结果明确零成员时，在新提交入库前拒绝新建；有成员时仍按容量接纳并允许繁忙排队；已有幂等键仍返回原记录。同步查询放在阻塞工作线程，不在每个创建请求中等待 broker。

用户已接受检测延迟及成员不等于立即空闲的限制。查询失败、样本过期或未取得样本是 unknown，不是零成员；本轮已确认 unknown 时暂拒新建并返回 503，见 R25。设计第 5.6 节只将其用于新建接纳，不凭在线观测终结已有任务。

成员观测使用独立后台任务、配置及专用缓存，创建服务读取该缓存执行接纳条件，不加入原健康采集、HTTP 或页面。两个任务的观测结果、错误、停止和缓存过期互不传播。本轮在此前维持健康机制的基础上新增 Kafka 探测需求，见 R20；它不合并成员观测缓存。原 Worker 健康协议字段及因旧业务 ACK 移除而涉及的指标问题仍留第 9 节审核。

### 3.3 已确认的交接窗口与重启规则

queued → dispatching 在 broker 发送确认之后执行。确认前数据库仍为 queued，临时发送失败保留本地队列与许可重试；进程退出后 queued 走原启动装入。broker 已保存但确认或状态更新未完成时可能重复发送，符合已接受的重复执行边界。

运行事件或终态可能先落库，之后的投递确认必须使用 queued 条件更新，不能回退状态。重启只重发 queued，为 dispatching 恢复待接纳许可但不重发，running 继续消费事件；不再统一标为 SchedulerInterrupted。这些状态处理已确认，具体启动停机编排留第 9 节审核。

此方案不需要新表、字段、持久发送标记或常驻扫描，也不消除入库与发送窗口。永久发送错误的终结规则留第 8 节审核，尚未进入代码实施。

后端重启不是 Worker 的执行中断：Worker 可能仍在执行，或已把终态保存在事件 topic。后端使用原事件消费组及已提交位点继续；终态入库后尚未提交位点的事件可重复读取，已有终态和审查初态不重复生效。恢复 queued/dispatching 许可只重建本地接纳数量，不占用或释放 Worker 沙箱位置。

若 queued 先收到合法 RUNNING 或终态，直接按条件更新。可能是投递确认尚未落库，也可能发送确认丢失或进程退出后仍保留 queued；不能仅凭该状态断言从未发送。不先补 dispatching，迟到投递确认不得回退 running/终态。

### 3.4 本期暂不处理的日志过期问题

Kafka 的 delete 保留策略会清理未消费的旧日志，实际清理并非逐条发送满 1 天即触发；见[日志保留配置](https://kafka.apache.org/43/configuration/topic-configs/#retention.ms)。删除日志不会自动把对应提交保存为失败。

用户决定本期忽略该业务收尾问题，将其记录为已知限制。此前讨论的位置关联、水位检测及自动过期失败均不纳入本期实现或验收；本期任务可能在消息被清理后继续保留非终态。

### 3.5 仅对 running 任务计时的再评估

用户询问能否仅对已进入 running 的提交计时，以避开繁忙或无 Worker 时的排队等待。这样确实排除了首次运行事件之前的排队，也能为后端等待终态设置上限；但 running 只表示曾收到合法运行快照，包括 PREPARING 和 COMPILING，并不证明源码此刻正在执行。

例如 A 已发布运行事件，之后失联且任务位点未提交；任务会被 B 重新取得，但 B 可能繁忙。数据库仍为 running，若继续原计时，这段重新排队也会被计入。另有 Worker 已正常完成、终态因发送或消费延迟而未落库的情况。因此计时到期可以定义为“系统不再等待”，不能当作实际程序超时或确定的 Worker 故障。

若采用，建议第一次合法 RUNNING 成功推进业务 running 时开始一次总等待计时；不因重复或阶段快照续期，预算覆盖既有执行、停止收尾及消息交接的余量。到期以现有终态条件写入系统执行失败，与实际终态遵循首次提交生效规则；它不取消沙箱，迟到的正确结果也不能覆盖已保存的失败。只按最近一条进度续期并不可靠，因为原快照没有周期心跳承诺，长时间没有阶段变化可以是正常执行。

后端重启后是否继续原计时也需要决定：当前没有持久化首次 running 的时间，创建时间不能替代；只用内存则重启会丢失原起点，可能重新等待一个完整预算。不能默认已有字段能恢复该计时。

本轮只评估，未确认引入。R11 及正文已确认的按事件等待做法暂不改变，计时器提案留在审核记录中。

### 3.6 第 6–7 节澄清与精简

设计第 5.6 节的 unknown 指后台缓存没有可用的新鲜成员数，与成功查询得到零成员不同。用户现已接受启动尚无样本或缓存不可用时暂拒新建；不据此终结已有任务或改变健康观测。

原“记录大小、协议及身份”表述过于笼统，现明确区分：

| 检查                               | 当前实现                                       | Kafka 接入变化                                             |
| ---------------------------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 编码消息大小、Protobuf 解码        | gRPC/Tonic 的消息上限和协议解码                | 在 Kafka 接收入口承担对应传输检查，具体上限仍属第 8 节提案 |
| Job ID、语言、源码、用例及资源限额 | WorkerService::validate_id / validate_job 已有 | 抽取复用现有校验，不重写一套                               |
| Kafka key 与负载 job_id 一致       | gRPC 没有 Kafka key                            | 已确认由发送端从负载直接派生，不增加接收端独立比较，见 R23 |

这里的 Job ID 校验是非空及字节长度约束，不是新增鉴权、UUID 格式验证或消息封装。语言及资源限制仍由现有输入合同决定。

第 6 节删除或收敛了单执行位置、执行期限细节、编译及用例循环、比较统计、工作目录释放、StopUnconfirmed 资源保留、BLOCKED 和停机停止通道的复述，改为引用 Worker 设计。保留的改动是 Kafka 接纳、运行快照发送、终态发布后提交位点、消费驱动、有界消息缓冲及分区变化处理。

第 6.2 节说明：A 的分区转给 B 时，A 的源码不会被 Kafka 自动停止，B 又可能读到同一条未提交任务。未执行则放弃、已执行则完成并发结果，但原执行不得再提交已撤销分区的位点；本轮已接受该策略，见 R18。断连也不直接等于撤销或判题失败。

第 6.3 节的安全停止和资源保留是现有合同；新增部分只有停止 MQ 新接纳，以及在单独消息预算内交接结果和位点。正文使用“不再接纳新任务”，避免将停止新接纳误写成立即停止交接所需的消费驱动。

第 7 节与 LLM 的关联仅是现有自动交接：[Scheduler 跟踪](../../crates/backend/src/scheduler/tracking.rs)已在机器终态落库前调用 prepare_automatic，并以 save_terminal 同时保存审查初态，之后由 Scheduler handoff。Kafka 事件消费者需要接替该调用方，原业务 ACK 调用处改为提交事件消费位点；LLM 客户端及队列不因此改走 Kafka。正文保留这一衔接及重复终态不重复审查，其他细节引用第 08 篇。

### 3.7 组检测间隔与健康地址发现

在本稿选用的 group.protocol=classic 下，rdkafka 0.39 随附的 librdkafka 2.12.1 默认 heartbeat.interval.ms=3000、session.timeout.ms=45000；broker 在距最近心跳超过会话期限后移除失联成员，而非每 3 秒就认定故障。后端 fetch_group_list 是另外的主动查询，不会直接接收每次心跳；采集周期和调用耗时会再增加观测延迟。后端每 5 秒查询可作为建议起点，尚未固定。max.poll.interval.ms 默认 300000 是消费驱动的处理存活约束，不是 Worker 判题期限。依据见[固定版本配置](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md)。

组描述能取得成员 ID、client_id、client_host 及分区分配，但没有 Worker 的 gRPC 监听端口。client_host 是 Kafka 看到的连接来源，不保证是后端可直连的健康地址，容器、NAT 和多 Worker 共用主机会影响推导；字段定义见 [DescribeGroups](https://kafka.apache.org/43/design/protocol/#The_Messages_DescribeGroups)。

若要取消后端地址列表，最小可讨论方案是 Worker 配置一个对后端可达的健康 RPC 公布地址，并通过任务消费者的 client.id 公布；后端从成员信息取得该地址后仍调用原 GetWorkerStatus，不新增业务消息。但这会让健康目标发现依赖消费组信息，离组成员也不再自然出现在活动名单中，需先确认是否接受这一范围变化。本轮用户已决定保留健康 RPC 及配置列表，地址发现选项暂不采用，见 R22。

### 3.8 key 检查、调用等待及客户端依赖

原接收比较拟由 Worker 检查任务 key、后端检查事件 key。用户质疑其必要性：两个生产者都由本项目控制，key 本来就应取自同一消息的 job_id，既有业务关联也使用负载 ID。在这一入口合同下，独立比较只能额外发现构造错误，并非结果幂等或任务路由的前提。

用户已采用精简方案：发送入口直接从待编码消息的 job_id 生成 key，不接收第二份独立 key 参数；接收端继续复用 Job ID 和业务上下文校验，不增加 key 对比或冲突失败路径，见 R23。

“Kafka 调用受消息预算限制”原意是网络交接等待有上限。第 7 节具体指数据库提交后等待事件位点提交结果，示例为 commit_timeout_ms=5000；失败或超时后仍完成已有自动审查的本地 handoff，不能无限等待。消息可能后来被确认或重复读取，不能据调用超时回滚机器结果，也不因此终结其他尚未完成任务。

发送还需区分进入客户端队列的等待与 broker 投递完成的等待；FutureProducer::send 的 queue_timeout 仅约束前者，delivery.timeout.ms 约束投递及内部重试。commit_timeout_ms 是应用等待参数，不是 librdkafka 配置名。位点提交实际完成结果仍由驱动报告，依据见[发送接口](https://docs.rs/rdkafka/0.39.0/rdkafka/producer/struct.FutureProducer.html#method.send)。

rdkafka 是 librdkafka 的 Rust 封装，经 rdkafka-sys 使用本地 C 库。建议用 cmake-build 构建随附源码并静态链接 librdkafka，构建环境准备 C/C++ 工具链、CMake、make 或 Ninja、pkg-config；保留默认 libz 时准备 zlib 开发环境。无需预装系统 librdkafka；若启用 dynamic-linking 则需安装匹配库并在运行环境提供动态库。TLS、本地构建和协议选择是不同事项，暂不考虑 TLS 仍需本地编译工具。未安装软件或实际编译该依赖。

第 8.1 节补充逐项参数用途，保留消费者关闭自动提交及自动保存位点的区分：store 只记录本地待提交位置，commit 才提交至 broker。生产者幂等不合并应用重复发送的同 ID 消息；acks=all 由幂等模式自动要求兼容值，显式保留用于表达发送合同。auto.offset.reset=error 会令首次没有位点的新组也报错，因此需要初始位点步骤；如希望简化首次部署，可另议 earliest，但它也会改变位点过期时的行为，本轮没有擅自更改。

### 3.9 Kafka 健康与整体部署

用户确认健康观测应包含后端与 Kafka 连通性或其他低成本指标。最小提案是在现有 health 采集内使用已有 Kafka 客户端，对两个既定 topic 查询 metadata，采用原周期、预算及新鲜度语义；快照增加 kafka 项，页面展示状态、完成时间、稳定错误，成功时可附分区数及 leader 可用信息。HTTP 只读缓存，不发送探测任务，不新增集群监控平台。元数据请求成功只覆盖其请求范围，不等于所有 broker、写入或消费流程都正常。

成员在线观测继续单独采集和缓存。Kafka 健康失败用于展示，不增加新的提交拒绝或已有任务失败规则；unknown 成员接纳已由 R25 确认为暂拒新建。健康 DTO 按正文最小范围实施；旧 ACK 指标曾按 R28 提出布尔字段，现按 R33、R34 的有界结果队列保留原数量／容量字段和前端数值展示，未修改现行第 07 篇合同或代码。

### 3.10 系统库安装与消费位点参数

用户询问能否通过 apt 等包管理器安装 librdkafka，避免源码编译。可以：安装 librdkafka-dev 与 pkg-config，rdkafka 启用 dynamic-linking，由构建脚本查找系统库。需要核对版本；rdkafka-sys 4.10.0+2.12.1 的构建脚本以 pkg-config 要求 librdkafka >= 2.12.1，不能只依据项目 README 的宽泛兼容描述判断。依据见[构建脚本](https://github.com/fede1024/rust-rdkafka/blob/v0.39.0/rdkafka-sys/build.rs)。

已只读查询当前 apt 索引，librdkafka-dev 候选为 2.13.0-1，满足该最低版本要求；没有安装或实际构建验证。正文将系统动态库和 Cargo 构建随附源码列为两种可选链接方式，不预先要求源码构建。当时只讨论可行性；本轮 R31 已确定默认动态并支持显式静态构建。

acks 的标准取值是 0、1、all/-1：分别不等待 broker 确认、等待 leader 本地写入，以及等待同步副本集合确认。显式启用生产者幂等时必须采用 all，librdkafka 在未设置 acks 时自动选用兼容值；若显式指定 0 或 1，则客户端配置失败。该轮只解释现有配置，不改变已选幂等方案。语义见[Kafka 生产者配置](https://kafka.apache.org/43/configuration/producer-configs/#acks)和[librdkafka 参数](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md)。

enable.auto.offset.store 控制消息交给应用时是否自动记下客户端内存中的待提交位点；enable.auto.commit 控制是否定期将位点提交到 broker。以收到 offset=100 为例，自动 store 可能先记下 101，但这一步本身没有持久消费进度。若随后自动 commit，而业务尚未完成，故障后就可能从 101 开始而跳过该任务。

本稿保持两项 false，在第 3.1 节的业务交接完成后直接提交明确分区的 offset+1，不增加手动 store 的步骤。若始终显式提交指定位置，auto.offset.store 不决定该次提交的位置；不能将其误解为第二道持久确认。接口见 [Consumer::commit](https://docs.rs/rdkafka/0.39.0/rdkafka/consumer/trait.Consumer.html#tymethod.commit)。

本轮保留 Worker 健康 RPC 与配置列表，采用精简 key，并把两个 topic 保留期从 7 天改为 1 天。日志过期后业务记录不自动失败的限制仍按 R14 延期；消息清理仍按日志段进行，不能把 1 天理解为逐任务超时。

### 3.11 最后决策回应与解释

本节保留上一轮说明；首次 PREPARING 确认前置、单份待发终态及 RPC 布尔化，已由第 3.12–3.13 节有界结果队列方案取代，不再作为待确认事项。

用户已同意 unknown 暂拒新建，及 Worker 无法向 MQ 发送终态时保留结果并重试，分别记为 R25、R26。后者仅保留一份本地终态，临时错误暂停新接纳并继续发送，不重新执行源码；停机收尾超时或不可继续的客户端故障不提交未确认的任务位点，允许重投。单次投递等待超时不自动将判题保存为失败。

运行快照合并仍为待确认提案：首次 PREPARING 必须先取得 broker 确认再开始执行；之后每个进度回调只更新一个“最新待发运行快照”位置，发送器空闲时取最新值，不为每次回调排队。最多另有一份已在途运行事件；终态生成后清掉尚未发送的中间快照，结束已有的有限发送等待后交接终态。终态独立保留并确认，不被进度覆盖。

例如执行器产生“运行第 1 例 → 检查第 1 例 → 运行第 2 例”，若发送器来不及处理，待发位置可直接更新为“运行第 2 例”。后端可能跳过中间阶段，与原轮询只取得当时快照的语义一致；既有合法状态仍全部可被接收。该方案不增加进度心跳、不要求前端展示进度，也不使执行器等待每次中间事件发送。

用户要求永久失败不应只终结 queued。本轮改为：后端能识别并关联的任务不可恢复失败允许 queued/dispatching/running 条件进入 failed，finished/failed 不覆盖。已有正常执行不会仅因一次多余重发失败而被断言为永久失败；运行状态本身也不能豁免真正失败。已落库失败不会远程取消程序，迟到正常结果仍不能覆盖。

Worker 不写数据库。若 Worker 永久失去 MQ 通信能力，后端没有立即收到其故障的渠道；只凭这一策略无法保证当时立即保存 failed。本稿不为此新增任务计时器、数据库旁路或通知 RPC，继续按已确认交接及重投合同处理。

用户接受原指标改为 MQ 交接状态，前端倾向布尔展示，并询问能否把 RPC 也改为布尔。本轮提出：移除 unacknowledged_results 和 unacknowledged_capacity，改为 has_pending_result；RPC 方法、停止标记、执行状态和地址配置保留，HTTP 与前端同步修改。true 表示本机有终态尚未获得 Kafka 发送确认；false 表示没有这样的终态。观测失败、unknown 或 stale 由外层观测状态表达，不显示为 false。旧字段编号保留不用，依据见 [Protobuf 删除字段说明](https://protobuf.dev/programming-guides/proto3/#deleting)。此处只修改提案，尚未修改 Proto 或生成代码。

用户已通过 apt 安装库；只读检查确认 pkg-config 返回 librdkafka 2.13.0，开发包同时有共享库及静态库。安装包不决定链接方式；默认随附源码静态构建不会自动使用已装系统静态库。动态链接是直接复用系统库的方便路径，系统静态链接还须处理传递依赖。本轮未做实际链接验证，也未将用户询问视为已选定动态链接。

8 个任务分区不要求 8 个 Worker。每个 Worker 消费者订阅同一 topic、加入同一组后，Kafka 可把多个分区分给一个成员：1 个 Worker 可拥有 8 个，2 个可各有 4 个，3 个通常为 3/3/2；具体分区编号由分配器决定。Worker 的一个执行位置保持不变，因此对应最多同时执行 1、2、3 个不同任务。分区数量均衡不保证任务耗时均衡；用户已在本轮接受首期单 broker 及 8/1 分区提案，见 R32。

### 3.12 逐用例进度、有界结果与构建选择

现有 [Executor](../../crates/worker/src/executor.rs)在 PREPARING、C 编译、每个用例的 RUNNING_CASE 和 CHECKING 阶段触发进度，并递增 completed_cases。[RPC 执行回调](../../crates/worker/src/rpc.rs)按 Job ID 更新 GetJobReply，GetJob 返回当时快照；后端轮询把合法中间阶段统一视为 Running。已有的是逐用例快照更新及查询，没有逐用例主动推送或前端进度展示。

协议区分 state 和 phase：编译和逐例执行时 state 都是 RUNNING，phase 细分为 PREPARING、COMPILING、RUNNING_CASE、CHECKING；完成时 phase=DONE，state 为 FINISHED 或 FAILED。因此合并是同一活动 Job 的多份中间快照保留最新值，不是合并不同判题任务。任务终态各自独立保留。

用户提出 MQ 交接失败时允许有界结果积压，以便继续执行并复用原协议。本轮方案只缓冲已完成的终态，不增加应用侧未执行任务队列，仍为单执行位置。复用 max_unacknowledged_results，开始执行前为结果预留名额，满时暂停接纳；结果发送器按 FIFO 发布终态并收尾任务位点。条目在完整交接结束后释放名额，因此消息已发布但位点尚未确认的条目也不会形成无界元数据积压。失去分区归属的条目按第 6.2 节不再提交旧位点，终态发布确认后即可释放。

原“PREPARING 发布确认后才执行”会在事件通道不可用时挡住下一任务，削弱结果缓冲目的。本轮配套建议撤回该前置等待：所有运行快照非阻塞更新，优先交接终态，执行由沙箱可用和结果名额控制。事件可能直到终态才首次到达后端，仍按已确认的 queued/dispatching 直接接受终态处理，不补造进度。

本地排入队列不提交任务位点；发布及允许的位点交接完成后才确认，且不能跨过同分区较早未交接记录。Worker 崩溃可能丢失内存结果，未提交位点使任务可重投，符合已接受的重复执行边界。结果交接临时失败可以继续重试，正常停机仍只使用一个有限总收尾预算，不增加结果落盘恢复机制。

该提案保留原 GetWorkerStatusReply 和 HTTP 的数量／容量，语义改为尚未完成 MQ 交接的终态条目数及实际配置上限。前端可按数量大于零显示待回传／无待回传，满足此前布尔展示偏好，无需新增布尔协议字段；先前 has_pending_result 提案不再推进。

用户指定 Cargo 默认动态并支持手动静态。拟在 backend 和 worker 暴露 kafka-dynamic、kafka-static 特性，前者默认启用 rdkafka/dynamic-linking，后者显式启用 rdkafka/cmake-build；静态仅指 librdkafka，使用 Cargo 自动构建随附源码，不默认链接系统静态库。工作区依赖只固定 Tokio，backend 的 worker 开发依赖关闭默认特性，防止静态测试重新启用动态模式。命令及特性规则依据见 [Cargo 特性文档](https://doc.rust-lang.org/cargo/reference/features.html)。未修改 Cargo.toml 或实际构建任一新模式。

用户同时明确接受不可恢复任务失败的所有非终态条件规则，以及原第七项单 broker、8 个任务分区、1 个事件分区、副本数 1、min.insync.replicas=1 的首期部署提案。
