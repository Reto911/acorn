# Kafka safe 位点确认路线研究

对应[Kafka 设计 v18](../10-kafka-judging-design.md)。本记录比较替代路线及其影响，尚未修改现行设计或生产实现。这里的 safe 指业务代码不直接操作原生指针；rdkafka 本身仍通过 FFI 使用 librdkafka。

## 1. 结论与路线

异步提交后读回位点可以仅使用现有依赖的 safe API，并保留有界等待。它确认的是“消费组的持久位点已覆盖本条记录”，与当前“取得本次提交的实际结果”存在区别；它也增加查询请求。因此它是可选的合同调整，不能作为完全等价的内部替换。

| 路线                         | 确认依据                           | 主要影响                                                                                 |
| ---------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| 当前显式结果队列             | 本次 OffsetCommit 的结果及分区错误 | 保留应用 FFI；一次提交请求，有界等待                                                     |
| safe 同步提交                | 同步 commit 的返回结果             | API 没有等待预算；外层超时不能取消已启动的阻塞任务，需要另行解决停机收尾                 |
| safe 异步提交后读回          | OffsetFetch 返回的组位点覆盖目标   | 可以使用原生有限查询超时；增加请求，改变成功及错误的解释                                 |
| SDK 提供 safe 的结果队列封装 | 本次提交的结果                     | 可保留现行语义和请求数量，但当前锁定版本没有该接口，需要依赖补丁或后续版本；不是现成替换 |

异步提交配合 ConsumerContext 回调曾在本项目真实检查中无法收到手动提交的结果。仅重新启用相同组合不能算解决；更换依赖版本或修复 SDK 后仍须重新验证。SDK 文档也区分了 Sync 等待 broker 与 Async 仅入队两种行为，见 [Consumer 接口](https://docs.rs/rdkafka/0.39.0/rdkafka/consumer/trait.Consumer.html)及 [CommitMode 源码说明](https://docs.rs/rdkafka/0.39.0/src/rdkafka/consumer/mod.rs.html)。

## 2. 接口与实现影响

### 2.1 可以保留的接口

后端的 Publisher、EventConsumer::new/run、EventProcessor::new/process 均可保留现有签名。EventProcessor::process 已接收确认 Future，数据库保存、许可释放、审查 handoff 与具体确认机制分离；替换不需要把 Kafka 查询带入数据库层。

HTTP、Protobuf、MySQL 表结构、topic、消费组名和现有 TOML 字段均无需调整。commit_timeout_ms 继续表达一次确认的总等待上限，不新增查询预算或轮询频率配置。共享 acorn-kafka 目前只提供配置及策略，本轮也没有因研究引入连接管理抽象或新依赖。

### 2.2 需要替换的内部行为

主要修改点是 [commit::confirm](../../crates/backend/src/scheduler/kafka/commit.rs) 及 [EventConsumer::confirm](../../crates/backend/src/scheduler/kafka/events.rs)：

1. 继续构造本条记录所属 topic/partition 的 offset+1；在数据库处理完成后，调用一次 commit(offsets, Async)。入队错误直接报告，入队成功仍不代表确认完成。
2. 在阻塞工作线程调用 committed_offsets，查询完全相同的 group/topic/partition。检查调用错误、分区错误和有效数字位点，读回值达到或超过目标才算确认；position、已拉取位置和分区日志末尾均不能替代它。
3. 若位点尚未覆盖目标，仅继续查询，不在每次查询时重新提交。查询间隔只作用于未达目标后的等待。
4. 从确认开始共用一个绝对期限，每次查询和间隔只使用剩余预算，包含工作线程排队时间。不能给每次查询重新分配完整的 commit_timeout_ms。
5. 移除当前自管的原生队列、事件及指针访问。内部 helper 可以继续返回 Result<()>；但其 Ok 和错误上下文须表达新的确认依据。

committed_offsets 的 Rust 接口接收 Timeout；原生 rd_kafka_committed 也在循环中使用剩余期限并复制请求数据，避免调用方超时后释放数据导致悬空访问。见 [rdkafka 查询实现](https://docs.rs/rdkafka/0.39.0/src/rdkafka/consumer/base_consumer.rs.html)和 [librdkafka 2.12.1 实现](https://github.com/confluentinc/librdkafka/blob/v2.12.1/src/rdkafka.c#L3622)。因此不必留下一个没有应用等待期限的同步 commit 阻塞调用。

查询仍是阻塞接口，不能直接放在 Tokio 异步执行线程上。外层 timeout 仍不取消已入队的提交或已发出的网络请求；有限查询预算约束的是调用方等待和临时资源的持有，不承诺 broker 同时取消操作。消费者关闭、重平衡及消费驱动仍由既有生命周期负责。

有限提交等待也不能单独证明整个消费者可以按时关闭：当前 SDK 的 BaseConsumer::drop 会驱动关闭直到 closed，这一共同收尾路径不因使用原生队列或 safe 读回而消失。K05 仍须按正式生命周期验证总停机预算，本次正常位点操作实验未验证故障关闭。

### 2.3 后续 Worker 接入

Worker 尚未实现该提交路径。若后续复用读回确认，结果队列的“待发布终态／待提交任务位点”阶段可以保持，但必须保留 K04 既定的原分区归属检查、撤销与重获归属规则。组位点已推进不能证明旧执行仍有提交权限，也不能代替消费驱动或恢复旧归属。

Worker 不能再仅凭本次 ConsumerCommit 错误码区分提交失败，因为读回不提供它。查询错误、确认超时及独立消费驱动报告的客户端故障须按各自来源处理；不能把每个查询失败都解释为任务位点未保存。

## 3. 规约与错误语义影响

### 3.1 需要明确调整的成功条件

当前[事件处理合同](../10-kafka-judging-design.md#7-后端事件处理)及[客户端预算](../10-kafka-judging-design.md#81-客户端与配置示例)要求等待本次提交结果。若采用纯位点读回，建议改为：

> 在确认总预算内，向 broker 查询并确认该消费组在指定分区的持久位点已覆盖本条记录，视为交接完成。仅提交入队成功不构成确认。

这不要求数据库、事件载荷或 Kafka 协议定义变更，但需要同步第 10 篇第 6–8 节、第 03 篇 7.4 节及第 08 篇 7.1 节的确认依据与错误描述。适用的验收条件也应表达“目标持久位点得到确认”，不能继续声称取得了原提交请求的结果。

### 3.2 成功与故障场景的区别

| 场景                                 | 当前结果队列         | 纯位点读回                                             |
| ------------------------------------ | -------------------- | ------------------------------------------------------ |
| 提交成功，查询也成功并覆盖目标       | 成功                 | 成功                                                   |
| 已收到提交成功，但读回失败或超时     | 可以确认成功         | 仍无法确认，返回查询错误或超时                         |
| 本次提交结果不明，但组位点已覆盖目标 | 返回提交错误或超时   | 可以确认覆盖目标，不证明由本次请求推进                 |
| broker 拒绝提交，目标位点仍未达到    | 可保留本次提交错误   | 可能只能等到确认超时；原提交错误不由 OffsetFetch 返回  |
| 其他成员已推进同分区位点             | 当前请求仍有自身结果 | 读回可能满足目标，不能据此认定当前成员或旧执行提交成功 |

OffsetCommit 与 OffsetFetch 是两个不同请求；后者返回组的 committed_offset、metadata 及自身错误，不返回此前提交请求的执行结果。见 [Kafka 4.3 协议](https://kafka.apache.org/43/design/protocol/)。因此日志需要区分“提交入队失败”“持久位点查询失败”“总预算内未确认”，保留实际来源，不能统一伪称 broker 拒绝提交。

SDK 还提供 safe 的位点 metadata 读写接口，可以提交唯一标记并读回匹配，以加强对某次写入的关联。但这会新增标记生成及比较规则；其他成员覆盖标记后，即使目标位点已推进也可能无法匹配。它仍不能获得原请求的错误，本轮没有把这一额外机制纳入最小方案，也没有对它作性能测试。

### 3.3 可以保留的业务合同

- 先完成必要的 MySQL 写入，再发起位点提交；写入失败不提交。
- 仍只提交已处理记录的 offset+1，串行处理不跨过未处理记录。
- 至少一次消费、固定 Job ID、首个有效终态不可覆盖及自动审查去重继续成立。
- 确认成功、失败或超时均完成已经保存的自动审查本地 handoff；无法确认时结束当前事件消费服务，不跨过本条继续处理。
- 位点未达目标、查询失败和确认超时都不能推断“broker 一定没有保存位点”。
- 首次组位点初始化、auto.offset.reset=error、关闭自动提交及自动保存位点、禁止自动建 topic 的要求保持有效。

本项目不会在运行时自动重置组位点；读回比较不能据此扩展成一般意义上的位点永远单调或跨分区比较。管理员重置、topic 重建等情况仍按部署合同处理。

## 4. 性能影响与小规模实测

### 4.1 实测方法和范围

使用当前 Compose 的单 broker，配置镜像为 apache/kafka:4.3.1；实测客户端为 rdkafka 0.39.0、动态 librdkafka 2.13.0。创建一个独立 UUID topic 和四个独立消费组，每条路线分别预热 10 次，再交错记录 100 次串行确认。

当前路线直接复用已提交版本的 confirm 实现。各组目标位点逐次增加；另外三条路线分别是 safe Sync、立即查询的 safe 读回，以及读到旧位点后等待 10 ms 再查询的 safe 读回。每次读回检查分区错误及目标值，单次总预算 5 秒。

这项实验仅测消费组位点操作，不订阅或处理业务消息，也不包含 MySQL、判题执行、消费组重平衡、HTTP 或端到端停机。计时在同一个阻塞线程内包围每次确认，未计入生产路径每次 spawn_blocking 的调度时间。没有以不可取消的 Sync 故障等待验证停机保证。

| 路线                      | 样本数 | 平均耗时 ms | P50 ms | P95 ms | 平均读回调用数 |
| ------------------------- | ------ | ----------- | ------ | ------ | -------------- |
| 当前原生结果队列          | 100    | 0.882       | 0.758  | 1.410  | 0              |
| safe Sync                 | 100    | 0.974       | 0.772  | 1.661  | 0              |
| safe 立即读回             | 100    | 1.165       | 1.013  | 1.746  | 1              |
| safe 未达目标后间隔 10 ms | 100    | 1.169       | 0.988  | 1.946  | 1              |

本轮两种读回路线均在第一次查询达到目标，10 ms 间隔没有实际触发。立即读回的平均确认耗时比当前路线增加约 0.283 ms、32%；这是本机正常情况下确认阶段的观测，不是完整判题吞吐的结论，也不能推断其他网络、负载或故障下的延迟。

四条路线共 440 次确认操作正常完成，随后收到独立测试 topic 与全部四个消费组的删除确认。

### 4.2 请求、延迟与资源推导

当前正常路径是一条 OffsetCommit；读回路线至少再发一条 OffsetFetch。若事件速率为 E、每条平均读回 n 次，相关逻辑操作数由约 E 增至 (1+n)E，不含心跳、metadata 和 SDK 内部重试。本轮 n=1，即相关请求数量约翻倍；这不表示整个 broker 的总请求量翻倍。

异步提交与查询可以在网络和 broker 内部部分重叠，耗时不能直接按请求数量乘倍数。跨主机 RTT、查询排队和限流都会影响额外成本；若需要多次读回，查询间隔还会增加确认延迟。故障下的查询次数需要由总预算及一个有限间隔限制，不能无休止快速轮询。

后端事件只有一个分区且串行处理，额外确认等待会延迟下一条事件及自动审查 handoff。当前事件的首次运行／终态已经先写库并释放判题许可，因此这部分释放仍不等待读回；HTTP 创建接口也仍只等待本地接纳。实际事件处理上限取决于数据库及确认阶段的合计耗时，本轮没有测出它的变化比例。

Worker 结果队列的条目在位点确认后才释放，所以更长的确认时间也会延长结果名额占用。对耗时判题未必明显，短任务和密集进度事件更容易受到影响；需要在实际链路中判断，不能从本轮位点微测量外推出判题性能。

safe 读回会增加客户端与 broker 的请求编码、分配和响应处理工作，也会延长阻塞工作线程的占用。保持单条串行确认时，应用内仍只需有界的位点列表和一个活动确认，不需要新增队列或连接池。

## 5. 建议和实施前验证

若优先让业务代码不直接维护 FFI，并接受以组持久位点覆盖目标作为成功依据，建议把异步提交后读回作为可实施路线，先限于后端已有确认边界，保留现有公开接口及配置。需要先确认第 3 节的成功和错误语义，再同步设计与实现。

若要求保留每次提交的原始错误及当前请求数量，应继续使用现有结果队列，或由 SDK 增加 safe 封装；safe Sync 加外层 timeout 不能独自满足有限资源收尾。Tokio 明确说明，已启动的 spawn_blocking 任务不能被取消，运行时关闭仍可能等待它，见 [spawn_blocking 文档](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。

实际替换时只需针对新机制验证：目标位点与分区错误的判定、共用总预算、确认失败仍审查 handoff，以及一项现有真实 Kafka 后端链路。复用现有事件／审查用例，不扩展为新的恢复机制或全面故障矩阵。Worker 的分区归属及队列检查仍在 K04 完成。

本轮只编译和执行了上述独立研究探针，并检查本记录的格式与本地链接；没有修改或重跑生产链路实现。静态链接、断连、重平衡、完整判题性能及新方案的集成验收均未验证。
