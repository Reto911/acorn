## 2. 实施前决策

以下决策已确认，具体合同见[审核记录第 3 节](../d01-review/11-user-authentication-review.md#3-最终决策)。本节勾选表示选项已确定，不表示依赖它的实施任务已经完成。

- [x] D02 接受 24 小时闲置滑动续期、每用户 10 条／全局 10000 条默认上限；Cookie 改为 24 小时持久 Cookie 并同步续期。用于 U02.2、U02.3。

## 3. 开发清单

总体顺序为 U01 → U02 → U03 → U04 → U05；组内依赖在条目中注明。各项相关检查随实现执行，U05 汇总结果并完成联调与交付。

### 3.1 U01 用户数据与密码

合同见[设计第 3 节](../11-user-authentication-design.md#3-用户数据与密码)。主要入口为后端 database、HTTP DTO 和新增 auth 模块，以及预置用户脚本。

- [ ] U01.1 定义注册、登录输入和公共用户 DTO，实现共用的用户名规范化及输入校验。依赖 D01；完成时注册与登录使用同一规范化规则，响应不包含密码哈希，客户端不能指定 role、status 或 user_id。
- [ ] U01.2 在 database/users 中实现按用户名读取和创建用户。依赖 U01.1；复用现有 users 表、SQLx 连接池和唯一索引，注册固定 student／active，重名转换为 UsernameTaken，其他数据库错误沿用既有处理。
- [ ] U01.3 在 auth 中实现 Argon2id 哈希与验证，生成带随机盐和参数的 PHC 字符串。复用 Tokio spawn_blocking；完成时密码计算不占用异步执行线程、不持有数据库连接或会话锁，不添加登录并发或失败次数限制。
- [ ] U01.4 为 [seed-user.sql](../../examples/seed-user.sql) 写入已知测试密码对应的真实 Argon2id 哈希，并在脚本注释中说明凭据。依赖 U01.3；保留原测试用户标识、role 和 status，不修改数据库结构版本。

### 3.2 U02 内存会话与认证接口

依赖 U01 的用户信息和密码能力；合同见[设计第 4 节](../11-user-authentication-design.md#4-session-与-http-请求边界)及[认证接口](../11-user-authentication-design.md#51-认证接口)。主要入口为 auth、HTTP、AppState 和配置加载器。

- [ ] U02.1 建立全局 LRU 和按用户索引的个人 LRU，以一把短锁保护并接入 AppState；实现安全随机 token、查找及同步删除两套索引的共用流程。依赖 D05；会话正文只存一份，用户索引仅保存 token 顺序，容器长度直接提供计数，用户无会话时删除其索引；锁不跨数据库、密码计算或网络等待。
- [ ] U02.2 实现过期判断、24 小时闲置续期及容量淘汰。依赖 U02.1、D02、D05；访问先判过期再更新活动时间和两套 LRU，新建时从全局旧端清理全部过期项，再替换浏览器旧会话，直接取得个人计数并先淘汰个人最旧项、后淘汰全局最旧项。清理允许 O(N)，清理后的每级容量淘汰最多一项；不扫描统计个人会话，容量满不拒绝登录。
- [ ] U02.3 实现持久 Cookie 设置、读取、续期和清除，并同步后端配置及示例。依赖 D02；登录及普通有效认证响应设置 Max-Age=86400，退出清零；http.cookie_secure 省略或 false 时使用普通 Cookie，true 时使用带 Secure 的 __Host- Cookie。public_origin 使用浏览器访问的外部 Origin，支持 HTTPS 反向代理连接 HTTP 后端。
- [ ] U02.4 接入 register、login、me、logout 四个接口。依赖 U01、U02.1–U02.3、D03；响应、状态码和业务错误沿用设计，登录成功新建会话、失败保留原会话，退出幂等且返回现有前端可解析的 JSON，me 可返回 user=null。
- [ ] U02.5 接入受保护路由的认证、预期用户比较和写请求 Origin 校验。依赖 U02.4，健康路由行为依赖 D04；无有效会话返回 401，预期用户不匹配返回 409 且不执行业务，来源不符返回 403；复用请求大小限制和错误结构，落实 no-store 及敏感字段不记录日志。

### 3.3 U03 个人提交与审查隔离

依赖 U02；合同见[设计第 5.2 节](../11-user-authentication-design.md#52-对现有业务的改动)。主要入口为 HTTP、submissions/creation、database/submissions 和 database/reviews。

- [ ] U03.1 将 AuthenticatedUser 的 user_id 传入 CreationService、创建事务及所有幂等查重分支。完成时提交归属来自已认证身份，继续复用 UNIQUE(user_id, create_request_key)，已接纳任务保留该身份。
- [ ] U03.2 为历史查询增加用户过滤，详情查询同时匹配提交 ID 和 user_id。完成时其他用户的记录不会出现在列表中，访问其详情与访问不存在的提交均返回 404；内部 Scheduler 查询保留原职责。
- [ ] U03.3 将 user_id 传入独立运行的手动审查操作，在 SELECT FOR UPDATE 时限定归属。完成时越权请求不读取或修改目标审查状态，自动审查及 Kafka 内部处理仍按提交 ID 工作，退出不取消已接纳操作。
- [ ] U03.4 移除 test_user.user_id 配置、调用方和启动时预置用户必须存在的检查，同步配置示例及受影响夹具。依赖 U03.1–U03.3；完成时业务无全局测试身份依赖，空用户表可启动并注册，内部启动恢复仍覆盖所有用户。

### 3.4 U04 前端登录与账号状态

依赖 U02、U03；合同见[设计第 6 节](../11-user-authentication-design.md#6-前端交互与本地数据)。主要入口为 API 客户端、Vue composable、App、路由及现有草稿与提交请求逻辑。

- [ ] U04.1 复用 requestJson 和 Vue composable 接入认证 API、启动时 me 查询及页面用户状态。完成时导航可显示当前用户并退出，受保护请求携带页面预期 user_id，前端不读取或存储 Session token。
- [ ] U04.2 复用 Element Plus 实现注册／登录表单及登录提示，接入提交、历史、结果和审查入口及直接访问路由。依赖 U04.1、D01、D03、D04；使用 ElForm／ElFormItem 的 rules 与 validate() 执行与后端一致的用户名、显示名及密码限制，Unicode 计数、字节数和空白规则使用自定义 validator；无效字段显示错误且不发送请求。未登录不展示私有内容，取消提示留在原页面，登录保留编辑内容且不自动提交或发起审查。
- [ ] U04.3 统一处理 401、409、退出和账号切换。依赖 U04.1；暂停旧轮询、取消请求并忽略迟到响应，保存旧账号草稿后清理私有页面状态；409 重新获取 me，不清除新账号的有效 Cookie，不自动重发旧账号的写请求。
- [ ] U04.4 为 [useDraft](../../web/src/composables/useDraft.ts) 的草稿及语言选择增加 user_id，并为 [useSubmissionRequest](../../web/src/composables/useSubmissionRequest.ts) 的待确认提交增加 owner_user_id 和按用户分键存储。依赖 U04.1，与 U04.3 联动；仅原用户可恢复草稿或手动重试原请求，不迁移旧格式、不增加通用清理机制。
